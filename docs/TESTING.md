# 🧪 Data Assistant — стратегия тестирования

**Проект:** ai-data-assistant
**Версия:** 1.0
**Дата:** 2026-08-13
**Статус:** Active — Deployment Validation пройдена, ручные E2E, программные проверки конвейера

---

## 🎯 1. Назначение

Этот документ фиксирует фактическую стратегию проверки работоспособности
Data Assistant:

- какие уровни проверки существуют;
- какое окружение требуется для каждого;
- сколько стоят (время, внешние вызовы, токены);
- какие команды запускать;
- как избежать ложных «работает» на существующем экземпляре вместо
  воспроизведения с нуля.

Стратегия — **Source of Truth** для оператора, интегратора и сопровождающего.

> **Важно.** В проекте **нет** pytest-набора unit/integration-тестов (см. §8
> roadmap). Подтверждение работоспособности строится на Deployment Validation
> (воспроизведение с нуля по `DEPLOYMENT_GUIDE`) + ручных E2E-сценариях +
> программных проверках локального артефактного конвейера. Этот раздел
> документирует реальное положение дел, а не желаемое.

## 🧩 2. Уровни проверки

| Уровень | Что проверяет | Внешние вызовы | Где описан | Стоимость |
|---------|--------------|----------------|------------|-----------|
| **L1. Deployment Validation** | воспроизведение с нуля в чистом окружении по `DEPLOYMENT_GUIDE` | зависит от сценариев (см. L3/L4) | `DEPLOYMENT_VALIDATION_REPORT.md` | время оператора; LLM-токены только для L4 |
| **L2. E2E-сценарии (ручные)** | сквозные пользовательские потоки в браузере | LLM-токены для чат-сценариев | `E2E_SCENARIOS.md` | LLM-токены |
| **L3. Артефактный конвейер (программно)** | upload → анализ → 4 типа графиков → DOCX → скачивание, локально без LLM | нет | `DEPLOYMENT_VALIDATION_REPORT.md` (приложение) | бесплатно |
| **L4. Верификация провайдеров** | реальный вызов LLM (OpenAI/GigaChat/Yandex) + `test_connection` | LLM-токены | `EXTERNAL_PROVIDERS.md`, `DEPLOYMENT_VALIDATION_REPORT.md` (приложение C) | LLM-токены |

### 🧪 2.1. L1 — Deployment Validation

Подтверждает, что проект **воспроизводим с нуля** исключительно по публичному
`DEPLOYMENT_GUIDE` в чистом окружении (новый VPS / ВМ / чистый Docker Host).
Существующий экземпляр разработчика не считается доказательством
воспроизводимости. Каждая Validation сопровождается отдельным отчётом
(`DEPLOYMENT_VALIDATION_REPORT.md`): шаг → действие → ожидание → факт →
PASS/FAIL. Критерий готовности проекта — успешная Validation.

### 🎬 2.2. L2 — E2E-сценарии (ручные)

21 сквозной сценарий в `E2E_SCENARIOS.md`: пользовательский контур (чат —
загрузка, анализ, 4 графика, DOCX, markdown, изображения, несколько файлов,
свободный диалог, GigaChat fallback) и операторский контур (`/admin` —
промпт, модель, пресеты, температура/seed, специализация, реестры,
статистика, structured_output). Скриншоты — human-in-the-loop (оператор снимает
по подписям).

### ⚙️ 2.3. L3 — Артефактный конвейер (программно, без LLM)

Локальный детерминированный путь, не тратящий токены: загрузка файла,
`AnalysisService` (метрики/NaN-профиль/инсайты), `ChartService` (все 4 типа
`CHART_TYPES` → PNG), `ReportService` (DOCX с метриками + графиками),
`/download/{artifact}` с корректным MIME. Проверяется программно
(`AIService`/`ChatService`/`ChartService` напрямую) — это ядро системы,
не зависящее от LLM. Часть сценариев `E2E_SCENARIOS.md` помечена
«проверяется программно».

### 🔌 2.4. L4 — Верификация провайдеров

Реальные вызовы LLM по каждому пресету: OpenAI (`gpt-5-mini`, structured
output, `test_connection`), GigaChat (`GigaChat-Max`, OAuth-адаптер,
free-text parse, `test_connection`), YandexGPT (routing + `x-folder-id`,
end-to-end требует API-ключа Yandex). Гейтируется секретами в `.env`
(`OPENAI_API_KEY`, `GIGACHAT_AUTH_KEY`). Без секрета — честная конфиг-ошибка,
не падение (`AIService.enabled=False`).

## 🛠️ 3. Требования к окружению

| Переменная | Назначение | Когда нужна |
|------------|------------|-------------|
| `OPENAI_API_KEY` | LLM для пресетов OpenAI/Yandex/«Свой» | L4 (OpenAI/Yandex) |
| `GIGACHAT_AUTH_KEY` | GigaChat OAuth-обмен | L4 (GigaChat) |
| `GIGACHAT_CA_BUNDLE` | TLS сертификата Минцифры (prod) | L4 (GigaChat prod) |
| `ADMIN_TOKEN` | доступ к `/admin` | L1/L2 (операторский контур) |
| `APP_HOST` / `APP_PORT` | хост/порт | L1 (локальный запуск) |

**Секреты только в `.env`** (gitignored, в образ не попадают). В `config.json`
секретов нет (проверяется в Validation: `config.json` не содержит
`api_key`/`auth_key`/`admin_token`).

## ▶️ 4. Команды проверки

```bash
# 1. Локальный запуск (dev-режим — публикует порт, live reload)
cp .env.example .env          # заполнить секреты
docker compose up -d --build
# http://localhost:8000  ·  http://localhost:8000/health

# 2. Production-пересборка (без порта, за обратным прокси)
docker compose -f docker-compose.yml up -d --build

# 3. Health
curl -s http://localhost:8000/health    # {"status":"ok",...}

# 4. Операторский контур (нужен ADMIN_TOKEN)
#    браузер: http://localhost:8000/admin  (HTTP Basic: admin / ADMIN_TOKEN)

# 5. Программная проверка конвейера (внутри контейнера, без LLM)
docker compose exec web python -c "from app.services.chart_service import ChartService; ..."
#    (см. E2E_SCENARIOS.md — сценарии, помеченные «проверяется программно»)

# 6. Чистое окружение — Deployment Validation по DEPLOYMENT_GUIDE
#    новый VPS / ВМ / чистый Docker Host, без знаний автора сверх документации
```

> Полная процедура воспроизведения с нуля — в `DEPLOYMENT_GUIDE.md`.
> Результат Validation фиксируется в `DEPLOYMENT_VALIDATION_REPORT.md`.

## 💰 5. Стоимость и цель каждого уровня

| Уровень | Цель | Ресурсы | Когда запускать |
|---------|------|---------|-----------------|
| L1 | Воспроизводимость с нуля | Чистое окружение + время | Перед публикацией, после изменения deploy/инфра |
| L2 | Пользовательские потоки в браузере | LLM-токены (чат) | Демо заказчику, регресс UI |
| L3 | Детерминированное ядро (графики/отчёты) | Бесплатно (локально) | Каждое изменение сервисов |
| L4 | Реальный LLM по провайдерам | LLM-токены | Перед deploy, при смене провайдера/модели |

## 🔒 6. Изоляция и безопасность

- **Секреты вне репозитория:** `.env` в `.gitignore`, в Docker-образ не
  попадает (проверяется в Validation).
- **`config.json` без секретов:** runtime-конфиг содержит только операторские
  параметры; `OPENAI_API_KEY`/`GIGACHAT_AUTH_KEY`/`ADMIN_TOKEN` туда не пишутся.
- **`/admin` за HTTP Basic:** если `ADMIN_TOKEN` не задан — `/admin` отключён
  (403).
- **Path traversal:** `/download/{artifact_name}` проверяет, что путь не выходит
  за пределы `output_dir`.
- **LLM-токены:** тратятся только на L2 (чат) и L4 (провайдеры); L3 бесплатен.

## 🚀 7. CI/CD рекомендации (дорожная карта)

| Стадия | Команда/действие | Условие успеха |
|--------|------------------|----------------|
| Lint/импорт | `python -c "import app.main"` | Без ошибок импорта |

| L1 | `DEPLOYMENT_GUIDE` в чистом окружении | Все шаги PASS |

> Автоматизация L3/L4 в pytest-наборе — roadmap (см. §8). До этого
> проверка — ручная + программная по сценариям.

## 🗓️ 8. Что отсутствует и почему (roadmap)

В текущей версии **нет** pytest unit/integration-набора:

- ядро (L3) проверяется программно и через Deployment Validation;
- LLM-зависимые сценарии (L2/L4) требуют секретов и проверяются вручную;
- добавление pytest-набора (маркеры `unit`/`integration`/`expensive` по канону
  APL) — следующий шаг зрелости: unit-тесты реестров/coerce-логики/парсера,
  integration-тесты чат-эндпоинтов с моками LLM, expensive — реальные вызовы
  по расписанию.

До появления pytest этот документ — честный контракт фактической стратегии:
Deployment Validation + E2E + программные проверки конвейера + верификация
провайдеров.
