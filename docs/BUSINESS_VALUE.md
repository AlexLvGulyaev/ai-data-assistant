# 💼 Data Assistant · BUSINESS_VALUE

**Проект:** ai-data-assistant
**Дата:** 2026-08-12
**Статус:** Бизнес-оценка кейса в рамке «портфельный актив + развёртываемая база под клиентские внедрения». Количественные показатели, помеченные `*`, — оценочные и требуют измерения в пилоте; коммерческая валидация не проводилась (см. [`PROJECT_STATE.md`](PROJECT_STATE.md)).

> Позиционирование: проект рассматривается **не как SaaS для энд-юзера**, а как
> (а) портфельная демонстрация компетенции для потенциальных заказчиков AI-автоматизации
> и (б) развёртываемая база, от которой стартует кастомное внедрение под конкретного клиента.
> Обоснование выбора рамки — в конце документа (§10).

---

## 🎯 1. Проблема

У двух аудиторий — разные боли, которые один проект закрывает с разных сторон.

### Со стороны бизнеса-заказчика (кому внедряют)

| Проблема | Последствие |
|----------|-------------|
| Аналитик/менеджер без навыков кода: CSV-выгрузка из 1C/CRM, нужен график/отчёт | Excel требует формул, сводных и сноровки; результат — долго и зависит от навыка |
| ChatGPT Code Interpreter недоступен или нежелателен | В РФ ограничен доступ к OpenAI; корпоративные данные нельзя грузить в публичный облачный сервис |
| Нет внутреннего инструмента под корпоративного AI-провайдера | YandexGPT/GigaChat есть, но готового «chat with your data» под них нет |
| Каждый разовый запрос на «анализ данных» строится с нуля | Дорого, долго, не переиспользуется |

### Со стороны интегратора (кто внедряет)

| Проблема | Последствие |
|----------|-------------|
| Каждое внедрение AI-ассистента по данным стартует с нуля | Высокая себестоимость и длинный time-to-deliver; маржа съедается разработкой |
| Нет переиспользуемого фундамента с проверенными паттернами | Повторяются одни и те же инженерные решения (промпт-менеджмент, контракты модели, операторская панель) |
| Нужна демонстрация компетенции для потенциальных заказчиков | Портфолио из кода без живого демо и архитектурной зрелости слабо продаёт |

---

## 💡 2. Решение

Self-hosted AI-чат для анализа данных (FastAPI + Jinja2 + HTMX + OpenAI-совместимый API): загрузка CSV/Excel/JSON/изображений, диалог на естественном языке, модель сама планирует действие (анализ, график, отчёт, сводка) и исполняет его локально. Графики (histogram/bar/line/pie) и DOCX-отчёты сохраняются как артефакты.

Архитектурные решения, составляющие ценность базы для внедрений:

- **Провайдер-портабельность** — любой OpenAI-совместимый endpoint через `OPENAI_BASE_URL` (OpenAI, YandexGPT, GigaChat и др.).
- **Runtime-конфиг оператора** — специализацию, модель, лимиты и другие параметры оператор меняет через веб-админку `/admin` **без пересборки и рестарта контейнера**.
- **Реестры как единый источник истины** — `ACTION_TYPES` / `CHART_TYPES` определяют валидацию, AI-enum и fallback из одной точки.
- **Structured output** — строгий контракт ответа модели через `json_schema` (strict) + fallback-парсер для провайдеров без поддержки.
- **Двухрежимный Docker Compose** — production (сборка образа) и dev/operator (монтирование исходников + `--reload`).

В рамке 1+2 ценность — не венд-продукт, а **готовый к доработке фундамент + живое демо компетенции** (публичный эндпоинт `https://data-assistant.alex-n8n.site`).

## 💰 3. Количественная бизнес-ценность

> 📌 Все показатели ниже — оценочные (`*`); коммерческая валидация не проводилась.
> Замер реальных цифр (токены, время аналитика, время внедрения) — первый шаг пилота (§9).

### ⏱️ 3.1. Для заказчика-внедрения: экономия времени аналитика

| Показатель | Без ассистента (ручной Excel) | С Data Assistant |
|------------|-------------------------------|------------------|
| Анализ + график + отчёт по новой выгрузке | 30–60 мин* (формулы, сводные, оформление) | 5–10 мин* (один запрос в чат + правки) |
| Порог входа | Нужно владение Excel/формулами | Естественный язык, навыки кода не нужны |
| Зависимость от провайдера | — | OpenAI не обязателен (YandexGPT/GigaChat) |
| Где обрабатываются данные | Публичный облачный сервис (или никак) | Self-hosted, данные не покидают контур |

**Пример для аналитика, делающего 10 таких выгрузок в неделю:**
- Без ассистента: 10 × 45 мин = 7,5 ч/нед.
- С ассистентом: 10 × 8 мин ≈ 1,3 ч/нед.
- Экономия: **~6 ч/нед**, **~300 ч/год** высвобожденного времени аналитика*.

### 🛠️ 3.2. Для интегратора: ускорение внедрения (главная ценность рамки 2)

| Показатель | С нуля | От этой базы |
|------------|--------|--------------|
| Time-to-deliver кастомного внутреннего data-ассистента | ~3–4 нед* (LLM-интеграция, промпт-менеджмент, графики, отчёты, админка, Docker) | ~3–7 дней* (настройка провайдера, специализация промпта, брендирование, деплой) |
| Переиспользуемые слои | — | реестры, runtime-config, structured output, HTMX UI, Docker, health, /admin |
| Себестоимость первого внедрения | полная разработка | доработка + интеграция |

Это самая защищаемая оценка в документе: архитектура (A–G + вариант 3) уже построена и протестирована; кастомизация сводится к конфигурации провайдера, специализации промпта и обвязке под данные клиента.

### 💵 3.3. Стоимость одного запроса к модели

| Статья | Стоимость |
|--------|-----------|
| Один ход диалога (mini-класс, контекст файла ~1–3k токенов) | ~$0,0005–0,005* |
| Эквивалент времени аналитика на тот же анализ | ~$5–15* (30–60 мин × $10–20/ч) |
| **Экономия на одном запросе** | **до ~99%*** по сравнению с ручным анализом |

> Зависит от провайдера, модели и размера контекста; при масштабировании требует мониторинга расходов (см. §8).

### 📈 3.4. Масштабируемость (для заказчика-внедрения)

| Масштаб | Аналитиков | Запросов/нед | Годовая экономия часов* |
|---------|------------|--------------|-------------------------|
| Малая команда | 1–2 | ~10–20 | ~300–600 ч |
| Средняя команда | 5–10 | ~50–100 | ~1 500–3 000 ч |
| Крупная/регулярная аналитика | 20+ | ~200+ | ~6 000+ ч |

## 🎯 4. Как создаётся ценность

### 🧑‍💼 Для аналитика/менеджера (энд-юзер внедрённого экземпляра)

- **Анализ без кода и формул** — график, метрики, отчёт из одного запроса на естественном языке.
- **Не нужна Excel-экспертиза** — порог входа снижен до умения описать задачу словами.
- **Артефакты остаются** — графики (PNG) и DOCX-отчёты скачиваются из чата, переиспользуются.

### 🏢 Для бизнеса-заказчика

- **Данные не уходят в публичный LLM-сервис** — self-hosted, обработка внутри контура.
- **Работает на корпоративном провайдере** — YandexGPT/GigaChat через `OPENAI_BASE_URL`, без зависимости от OpenAI.
- **Оператор меняет поведение без программиста** — специализация, модель, лимиты через `/admin` в runtime.

### 🛠️ Для интегратора

- **Переиспользуемый фундамент** — реестры, runtime-config, structured output, Docker, HTMX UI уже готовы.
- **Сокращение time-to-deliver** — первое внедрение за дни, а не недели (§3.2).
- **Проверенные паттерны** — промпт-менеджмент с mtime-кешем, fallback-парсер, двухрежимный compose.

### 👀 Для потенциального заказчика AI-автоматизации (потребитель портфеля)

- **Живое демо компетенции** — публичный эндпоинт с реальной работой модели, а не код в репозитории.
- **Архитектурная зрелость** — A–G + вариант 3 видны в коде и документации: провайдер-портабельность, строгие контракты, операторская панель.
- **Самодостаточный публичный репозиторий** — можно развернуть и проверить самостоятельно.

## 🆚 5. Отличия от типовых решений

| Критерий | ChatGPT Code Interpreter / Excel Copilot | Data Assistant |
|----------|------------------------------------------|----------------|
| Деплой | Облачный сервис поставщика | Self-hosted (Docker) |
| Данные | Грузятся в публичный сервис | Остаются в контуре заказчика |
| Провайдер | OpenAI / Microsoft | Любой OpenAI-совместимый (вкл. YandexGPT, GigaChat) |
| Операторская панель | Нет | `/admin` — параметры в runtime без рестарта |
| Кастомизация под клиента | Нет | Открытый код, реестры, версионированные промпты |
| Стоимость | Подписка/токены поставщику | Только токены своего провайдера |
| Мощность анализа | Очень высокая (код-интерпретер) | Скромнее: заданные типы графиков/отчётов |

**Где уступает:** мощностью и богатством анализа (Code Interpreter исполняет произвольный Python; здесь — фиксированный набор действий из реестра). **Где выигрывает:** self-hosted, корпоративный провайдер, операторский контроль, кастомизация под клиента. Это нишевые, но реальные преимущества для B2B/внутренних внедрений — не для энд-юзерского SaaS.

## 🚀 6. Сценарии применения

- **Внутренний data-ассистент для SMB** — аналитики/менеджеры с CSV-выгрузками из 1C/CRM, YandexGPT как провайдер.
- **Корпоративный инструмент с защитой данных** — self-hosted, данные не покидают контур; для комплаенс-чувствительных отраслей.
- **Вертикальные сборки на базе** — аналитика продаж, операционная аналитика, отчётность по выгрузкам (специализация промпта + реестры под вертикаль).
- **Демонстрация компетенции** — живое демо для потенциальных заказчиков AI-автоматизации; кейс в портфеле.

## 🏢 7. Целевые заказчики

- **Российские SMB** с YandexGPT/GigaChat-подпиской, которым нужен внутренний анализ данных без OpenAI и без выгрузки данных в публичный сервис.
- **Предприятия с требованиями к конфиденциальности данных** — self-hosted обработка внутри контура.
- **Интеграторы и AI-фрилансеры** — переиспользуемая база для кастомных data-ассистентов; сокращение time-to-deliver.
- **Заказчики, оценивающие компетенцию** по AI-автоматизации — портфельное демо + архитектурная зрелость.

## ⚠️ 8. Риски и ограничения

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Конкуренция с ChatGPT/Excel Copilot в энд-юзерском сегменте | Высокое | Не позиционировать как SaaS для энд-юзера; фокус — self-hosted/B2B/кастом (§10) |
| Коммерческая валидация не проводилась | Высокое | Пилотный замер оценочных показателей на реальном внедрении (§9) |
| Чат открыт — нет аутентификации пользователей | Высокое для production | Добавить аутентификацию перед production-эксплойтом (см. [`SECURITY_NOTES.md`](SECURITY_NOTES.md)) |
| `storage/` — локальный volume, не горизонтально масштабируемый | Среднее | Persistent/shared storage для масштабирования |
| Мощность анализа скромнее Code Interpreter | Среднее | Расширение реестра действий / вариант 4 (декларативный движок графиков) |
| Расходы на LLM растут с масштабом | Среднее | Выбор модели, лимиты в runtime, мониторинг расходов |
| Оценочные цифры не подтверждены | Среднее | Измерить в пилоте: время аналитика, токены, time-to-deliver |

## ⚖️ 10. Почему рамка 1+2 (а не вертикальный SaaS)

Открытое обоснование выбора позиционирования — чтобы документ не строился на иллюзии.

«Поговорить с данными» — пространство, где ChatGPT, Claude, Excel Copilot, Google Sheets + Gemini уже免费/дёшево и очень хороши. Голый «chat with CSV» как SaaS для энд-юзера моты не имеет — гиганты давят мощностью и ценой. Поэтому третья рамка (вертикальный SaaS) отвергнута как целевая: она требует полноценной go-to-market (дистрибуция, онбординг, поддержка, ценообразование) и валидации спроса, которых пока нет.

Рамки 1+2 выбраны, потому что **архитектура под них и заточена**:
- провайдер-портабельность, runtime-конфиг оператора, реестры, structured output — это паттерны **B2B/кастомного внедрения**, не энд-юзерского SaaS;
- живое демо + самодостаточный публичный репозиторий — это **портфельный актив**, генерирующий доверие и запросы на AI-автоматизацию;
- переиспользуемые слои — это **база для внедрений**, снижающая себестоимость и time-to-deliver.

Если пилот (§9) покажет реальный спрос в конкретной вертикали, рамка 3 может быть переоткрыта — с измеренным рынком, а не гипотезой.
