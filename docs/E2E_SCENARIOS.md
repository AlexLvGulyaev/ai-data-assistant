# 🎬 Data Assistant — сквозные бизнес-сценарии

**Проект:** ai-data-assistant
**Дата:** 2026-08-13
**Статус:** as-built

---

## 🎯 1. Назначение

Этот документ содержит сквозные бизнес-сценарии Data Assistant без технических
деталей. Используйте его для ручного E2E-тестирования, демонстрации заказчику и
подготовки скриншотов.

Сценарии разбиты на два контура:

- **Пользовательский контур (чат)** — загрузка файла, анализ, графики, отчёты,
  свободный диалог с моделью.
- **Операторский контур (админка `/admin`)** — заменяемые параметры: системный
  промпт, модель LLM, провайдер, температура/seed, специализация; реестры агента
  и статистика использования.

> Скриншоты — human-in-the-loop: оператор снимает их в браузере по ссылкам
> `screenshots/…` и сверяет с подписью. Каталог медиаматериалов — в
> [`screenshots/MEDIA_INDEX.md`](screenshots/MEDIA_INDEX.md). Сценарии
> написаны по живой системе: локальный артефактный конвейер (upload → анализ →
> 4 типа графиков → DOCX → скачивание) проверен программно и работает.

## 📤 2. Загрузка CSV и preview

**Участники:** пользователь, публичный Web UI Data Assistant.

**Цель:** загрузить таблицу и получить preview первых строк и статистику.

**Шаги:**

1. Пользователь открывает [▶️ главную страницу](https://data-assistant.alex-n8n.site).
2. В зоне загрузки выбирает `examples/sample_sales.csv`
   (колонки `date, region, category, revenue, orders, margin`).
3. Нажимает **«Загрузить и открыть preview»**.
4. Backend сохраняет файл, определяет типы колонок, строит preview.
5. Открывается страница preview: первые строки таблицы, мета
   (строки/колонки/numeric), кнопки действий.

**Ожидаемый результат:** preview таблицы с метаданными; файл стал «активным».

## 💬 12. Свободный диалог: модель сама выбирает действие

**Участники:** пользователь, AI-ассистент (LLM).

**Цель:** задать вопрос на естественном языке и увидеть, как модель сама
планирует действие (анализ/график/отчёт/сводка).

**Шаги:**

1. С активным файлом пользователь пишет в чат:
   «дай сводку по выручке и построй самый показательный график».
2. Backend отправляет контекст файла + системный промпт в LLM (structured
   output: модель возвращает `action` + параметры).
3. Модель выбирает действие (например, `chart` + тип/колонки) и обоснование.
4. Backend исполняет действие локально и возвращает результат в чат.
5. В чате — текст-обоснование + результат (график/анализ/отчёт).

**Ожидаемый результат:** модель сама выбрала действие, результат исполнен
локально и показан в чате.

> Этот сценарий требует реального вызова LLM (токены модели). Проверяется
> оператором в браузере на живом демо.


![Свободный диалог: модель выбрала действие](screenshots/ADA_chat_free_dialog.png)

*Свободный запрос — модель сама выбрала действие и обоснование.*

**Ожидаемый результат:** график построен через fallback-парсер; лейбл
провайдера корректен (GigaChat, не OpenAI).

> Требует реального вызова GigaChat (токены). Секрет `GIGACHAT_AUTH_KEY` —

## 🗂️ 19. Реестры агента (read-only)

**Участники:** оператор, консоль `/admin`.

**Цель:** увидеть разрешённые действия и типы графиков — функциональное ядро
ассистента.

**Шаги:**

1. В правой колонке оператор видит секцию «Реестры агента» (прижата к
   Runtime-конфигу, без зазора).
2. Две под-панели: **«Действия»** (ACTION_TYPES) и **«Типы графиков»**
   (CHART_TYPES) — видимое название + кодовый ключ.
3. Секции read-only: добавление нового типа графика требует правки кода
   (`app/services/registries.py`) — вынос в редактируемые параметры в roadmap.

**Ожидаемый результат:** реестры показаны read-only, рядом с Runtime-конфигом.

## 📈 20. Статистика использования

**Участники:** оператор, консоль `/admin`.

**Цель:** увидеть расход запросов/токенов и ошибки.

**Шаги:**

1. Оператор открывает `/admin` — вверху дашборд статистики.
2. Видит счётчики: `total_requests`, `total_errors`, токены
   (prompt/completion/total), время последнего запроса/ошибки.
3. После нескольких чат-запросов и перезагрузки `/admin` счётчики растут.

**Ожидаемый результат:** дашборд отражает реальную активность чата; токены
отражаются, если провайдер возвращает `usage`.

## 🔒 21. structured_output: вкл/выкл

**Участники:** оператор, чат.

**Цель:** продемонстрировать строгий контракт ответа и его отключение для
провайдеров без поддержки.

**Шаги:**

1. Оператор переключает «structured_output» (в полях провайдера).
2. Нажимает **«Сохранить настройки»**.
3. При вкл — модель отвечает по `json_schema` (строгий контракт); при выкл —
   fallback-парсер разбирает свободный ответ.

**Ожидаемый результат:** флаг сохранён; поведение следующего ответа меняется
(строгий JSON vs fallback-парсинг).
